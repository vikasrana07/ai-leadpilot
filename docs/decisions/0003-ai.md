# ADRs: Phase 4 (AI)

## ADR-0018: The model never acts directly; every action is a validated, tenant-bound tool call
**Decision.** The orchestrator exposes up to ten tools. For each call the server checks, in order: the tool exists → it is enabled for this tenant → arguments validate against a **strict** schema (unknown keys such as `tenantId`/`leadId` are rejected, so the model cannot even *name* another tenant's records) → an idempotency key (same run + tool + arguments returns the stored result) → execution inside a tenant-scoped transaction (RLS applies). The tenant, conversation and lead come from the server-side turn context, never from model output. Every execution writes an evidence row (`ai_tool_executions`) and an audit entry. Failures are returned to the model as results rather than thrown. Scheduling tools exist but are refused until the appointments module ships (phase 5), so the model cannot invent availability.
**Consequences.** Prompt injection can at worst cause *allowed* tool calls on the *current* lead. It cannot reach another tenant or invoke anything outside the enabled set. Strict schemas mean the model sometimes needs a retry on malformed calls, which the loop handles.

## ADR-0019: Output guards before anything reaches a customer
**Decision.** A reply is released only if it passes deterministic checks: every money amount must appear in the tool results, retrieved knowledge or business facts (any rupee/lakh/crore format, 1% tolerance); URLs and phone numbers must appear in those facts; the confidential canary from the system prompt must not appear; length is capped at a sentence boundary. One corrective retry is allowed; a second failure hands the conversation to a person and sends the owner's fallback message. Deterministic gates run **before** any model call: keyword handover, monthly token cap, platform kill switch.
**Consequences.** Invented prices cannot be sent even if the model is compromised or hallucinates. False positives (a correct but unsupported figure) degrade to a handover, which is the safe failure.

## ADR-0020: Untrusted text is data: delimiting, ingestion-time sanitising, and no instruction channel from documents
**Decision.** Customer messages and retrieved passages are wrapped in `<customer_message>` / `<knowledge>` blocks (closing tags stripped from the content) and the system prompt declares them data. Sentences in uploaded documents that look like commands aimed at an AI ("ignore all previous instructions", "reveal your prompt"…) are removed **before indexing**, and the owner is told how many were left out. Retrieval is tenant-isolated twice (explicit filter plus RLS).
**Consequences.** Found by test: without ingestion-time stripping a poisoned document's sentence was echoed to customers. The pattern list is heuristic and will need maintenance; it is defence in depth, not a guarantee.

## ADR-0021: Untrusted file parsing runs in an isolated worker thread
**Context.** Bug found in phase 4: processing a PDF made `jose` fail every JWT verification afterwards, because pdf.js patches `Uint8Array.prototype`.
**Decision.** PDF and DOCX extraction runs in a throw-away `worker_threads` worker (own realm, 384 MB heap limit, 30 s timeout, killed afterwards). Text and CSV are parsed in-process. Uploads are also validated by extension, declared type **and** magic bytes, virus-scanned (ClamAV over TCP, **fail closed** when unreachable), then stored under a server-built tenant prefix.
**Consequences.** A malformed or hostile file can crash or hang only its worker, never the API, and cannot alter the API's built-ins.

## ADR-0022: Provider abstraction with an honest offline mock
**Decision.** `LlmProvider` / `EmbeddingProvider` are interfaces; `AI_PROVIDER=openai` uses the real client (Chat Completions with strict function tools, Embeddings), `mock` uses a deterministic rule-based stand-in plus hashed bag-of-words embeddings. The mock is **not a language model**: it exists so the full pipeline can run and be tested offline. Production refuses to start with `mock`, mock scanning, or mock WhatsApp. The UI shows a "Demo mode" banner whenever the mock is active.
**Consequences.** All 26 offline eval cases pass, which validates tools/guards/scoring/handover, but **says nothing about real model quality**. The live OpenAI client has never been run: no key was available.

## ADR-0023: Scoring is rule-based, explainable, versioned; temperature is derived
**Decision.** Defaults from the brief (15/15/30/15/25; Hot 70+, Warm 40–69, Cold below), configurable per tenant, saved as immutable versions and re-applied to all leads. "Unknown" is distinct from "not met": missing data adds nothing and is never negative; a lead with no signal stays *Unscored*, not Cold. Managers can override with a mandatory reason (history + timeline + audit); an override survives automatic re-scoring until cleared. Because temperature is derived from the score, the free-form "temperature" field was removed from lead create/update.
**Consequences.** Every score can be explained signal by signal. Moving thresholds re-scores all leads in small chunks.

## ADR-0024: Inbound ordering uses server receipt time; each AI run records what it answered
**Context.** Found in phase 4: WhatsApp timestamps have 1-second precision, so a customer message sent in the same second as our reply sorted *before* it; and a message arriving while the assistant was composing was sorted before its reply and never answered.
**Decision.** Messages use server receipt time for ordering (provider time is kept only for the 24-hour window). Each completed run stores `answeredThrough` (the newest customer message id it considered); the next turn answers everything after it, and unanswered messages are placed last in the model's history.
**Consequences.** No message is lost or double-answered under concurrency; the "one running turn per conversation" lock is a unique partial index.

## ADR-0025: Infrastructure notes
Local dev uses the legacy Bitnami MinIO image (the official `minio/minio` image is no longer pullable from Docker Hub) and ClamAV under amd64 emulation on Apple silicon. Production targets real S3. The shadow database used by `prisma migrate dev` connects as the superuser because creating the `vector` extension requires one; on managed Postgres the migration role must be allowed to `CREATE EXTENSION vector` (RDS: `rds_superuser`).
