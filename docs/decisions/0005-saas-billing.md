# ADR-0033 to 0040: plans, billing and the platform console (Phase 6)

Status: accepted (2026-11-16). **Razorpay is implemented against its documented API but has never been called for real**; see "Not verified".

## ADR-0033 Plans and entitlements are database rows
`plans` + `plan_entitlements` (global tables). Five numeric limits (`seats`, `ai_tokens_monthly`, `whatsapp_messages_monthly`, `active_automations`, `knowledge_mb`; NULL limit = unlimited) and four features (`ai_assistant`, `automations`, `web_widget`, `csv_export`). The catalogue of keys is in `@leadpilot/validation`; a plan must define every key (the API rejects a plan with a missing one, and a missing row at runtime means "deny", never "unlimited"). Seeds: `internal` (unmetered, hidden), Starter ₹4,999, Growth ₹9,999, Premium ₹14,999 ex-GST with the quotas in `unit-economics.md`. Platform admins edit plans in the console; nothing about plans is hard-coded in the web app.
**Price changes** do not touch existing subscribers: Razorpay plans are immutable, so a new provider plan is created lazily at the next subscribe (`razorpay_plan_amount` records what the cached provider plan was made with).

## ADR-0034 One place answers "what may this workspace do": `EntitlementsService`
Effective status is derived from dates as well as the stored status (trial past its end, grace past its end, cancelled period past its end all read as `EXPIRED` immediately, even before the minute job has persisted it). Enforcement is in the backend only:
- `PlanGuard` (global, after tenant resolution): `EXPIRED` ⇒ every non-GET returns **402 `subscription_required`**; `@RequireFeature(key)` ⇒ **402 `feature_not_in_plan`**; `@BillingExempt()` keeps billing and notifications working so a lapsed customer can pay.
- Limits: seats (members + pending invitations, also on reactivation), active automations (on enable), knowledge MB (on upload), outbound WhatsApp per month (inside the sending transaction), AI tokens (the tighter of the owner's own cap and the plan allowance; hard stop → handover).
- Non-HTTP paths enforce too: the AI orchestrator hands over instead of calling the model on a lapsed workspace or a plan without the assistant; automations create no runs; automated sends throw 402.
Quota failures are **402 `quota_exceeded`** with `details` naming the limit. Existing data over a reduced limit stays (nothing is deleted); only *adding more* is blocked.
**Read-only, not locked out** on lapse: customers can still view and export their data and reach billing. Nothing is deleted on lapse.

## ADR-0035 Subscription lifecycle
`TRIALING → ACTIVE ⇄ PAST_DUE → EXPIRED`, `ACTIVE → CANCELED (access to period end) → EXPIRED`. New workspaces start on `SIGNUP_PLAN` (default `internal` = unmetered, so self-hosting and tests are unaffected; production sets e.g. `growth` to give every signup a trial of that plan with no payment method). Failed renewal (`subscription.pending` / `halted`) starts a grace period (`BILLING_GRACE_DAYS`, default 7): everything keeps working, owners get an in-app notice and an email, and after the grace the workspace becomes read-only until a payment succeeds. A trial ending, a trial ending in ≤ 3 days, lapse, and quota thresholds (80% / 100%) notify owners exactly once each (event marks), via the minute scanner.

## ADR-0036 Webhooks are the source of truth; verification, de-duplication, idempotency
`POST /webhooks/razorpay`: HMAC-SHA256 of the **raw body** with `RAZORPAY_WEBHOOK_SECRET`, constant-time compare (401 on failure, nothing parsed first). Each event is stored in `billing_events` with a unique `(provider, event_id)`; a repeat of a processed event returns `duplicate`. Beyond that every handler is itself idempotent: payments are unique by provider payment id, so a retry delivered under a *new* event id still yields one invoice. Events for one workspace are serialised with `SELECT … FOR UPDATE` on its subscription row. Unknown or superseded subscription ids are acknowledged (200) and recorded as `ignored`, so the provider stops retrying. A processing failure returns 5xx so Razorpay retries. A late `charged`/`activated` never revives a cancelled subscription. The tenant is resolved from the provider subscription id by a narrow `SECURITY DEFINER` function (never from the payload's `notes`).
Checkout never activates anything client-side: the browser opens Razorpay's checkout, and activation arrives by webhook.

## ADR-0037 GST invoices
One invoice per captured payment, immutable (the app role has no UPDATE/DELETE on `invoices`). Numbers `LP/<FY>/<6 digits>` are gap-free per Indian financial year via `next_invoice_number()` (a counter row updated inside the invoice transaction, so a rollback rolls the number back; concurrent allocations serialise on the row; tested with 5 simultaneous payments). Amounts: the provider charges the GST-inclusive price; the invoice splits it at 18% into taxable value and tax, **CGST + SGST halves when the buyer's state equals the seller's (`SELLER_STATE_CODE`), IGST otherwise**; buyer and seller details are snapshotted onto the invoice. Buyer details come from the tenant's billing profile (legal name, GSTIN optional, state, address; GSTIN format and state-prefix agreement are validated; we do not call the GSTN portal). **The SAC code (`INVOICE_SAC`, default 998314) and the invoice layout have not been reviewed by a chartered accountant; do that before issuing real invoices.** Invoices are an HTML page the browser prints to PDF (no PDF dependency was added).

## ADR-0038 Plan changes and proration
Upgrade: applied immediately (`schedule_change_at: now`; Razorpay decides proration). Downgrade: scheduled for the end of the cycle (`pending_plan_key`, applied by the renewal payment) and **refused up front if current usage exceeds the target plan's limits**, with the exact items to reduce, so a customer is never silently stranded over a limit. Cancel: at period end (access continues; resubscribing schedules the first charge for when the paid period ends). A trial cancelled before paying simply ends on its date.

## ADR-0039 Platform console is a separate surface (refines ADR-0003)
`platform_admins` is its own table (not `users`), with its own login (`/platform/auth/login`, argon2id, lockout after 5 failures, identical errors), its own JWT secret **and audience** (`PLATFORM_JWT_SECRET`; unset = console disabled), a strict-same-site httpOnly cookie, a 30-minute token, an admin-row re-check on every request (disabling takes effect on the next call), and CSRF coverage. Tenant tokens do not open the console and console tokens do not open tenant routes (tested). Admins are created only out-of-band by the schema owner (`pnpm --filter @leadpilot/database platform:create-admin`); the app role cannot insert them. Every action (suspend/reactivate, plan assignment, plan edits, logins) is appended to `platform_audit_logs` with a required reason, and tenant-affecting actions are mirrored into the tenant's own audit log. `platform_audit_logs` has RLS that makes it visible only when **no tenant is in scope**.
**Deviation from ADR-0003:** a separate *database role* for the console was not created. Cross-tenant reads are four narrow `SECURITY DEFINER` functions (`platform_tenant_overview`, `platform_metrics`, `platform_set_tenant_status`, `billing_tenant_for_subscription`), the same pattern as the Phase 5 job helpers; per-tenant detail uses an ordinary tenant-scoped transaction. This keeps one connection pool and the smallest possible cross-tenant surface.
**Impersonation is not built.** It is the riskiest feature in the console; it needs its own review (time limit, reason, visible banner, read-only default). Deferred.

## ADR-0040 Scope of Phase 6
Built: plans/entitlements, subscriptions, Razorpay (mock + live client), GST invoices, dunning/grace, trial, gating, quotas/alerts, platform console, billing UI.
**Deferred, with reasons** (tracked in `PROGRESS.md`): Embedded Signup and Google Calendar (both need real provider apps/credentials to build honestly and are independent of billing), public API + outbound webhooks, compliance workflows (consent/export/erasure/retention), the remaining report set, impersonation. Starting any of them needs your decision on credentials or scope.

## Not verified
