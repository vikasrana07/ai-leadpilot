# ADR 0012: WhatsApp Embedded Signup (platform Meta app)

Status: **milestones 1 (backend), 2 (web) and 3 (health, Meta callbacks, template sync) built, mock only, off by default. Nothing here has been run against Meta.** Plan: milestone 4 (live verification with a real Meta test account).

## ADR-0075: one LeadPilot-owned Meta app for Facebook-connected numbers; manual connection stays
**Context.** A tenant had to create their own Meta app and paste phone number ID, WABA ID, a token and the app secret (ADR-0013, per-tenant app and secret). That is the biggest setup hurdle for non-technical owners. Embedded Signup lets the owner connect their own WhatsApp Business account through a Meta pop-up; LeadPilot receives a one-time code, exchanges it for a token, and uses ONE platform Meta app ("Tech Provider") for every tenant. Tenants still pay Meta directly (unchanged).

**Decision.**
- **Two connection modes per channel**, stored in `channels.config.mode` (`manual` is the default and means every existing channel): `manual` keeps its per-channel webhook URL, verify token and per-channel app secret (sealed `{accessToken, appSecret}`); `platform` has a sealed `{accessToken, mode}` only and uses the platform app secret from the environment (`META_APP_SECRET`). Manual connection stays available as the "use my own Meta app" fallback.
- **One platform webhook.** Meta allows one callback URL per app, so the platform app delivers to `GET/POST /webhooks/whatsapp` (no key). It is authenticated by `X-Hub-Signature-256` with `META_APP_SECRET`; the handshake uses `META_WEBHOOK_VERIFY_TOKEN`. Each change is routed to its workspace by `metadata.phone_number_id` through the SECURITY DEFINER function `find_channel_by_phone_number_id()` (returns channel id, workspace id, status and mode, nothing else). A number that belongs to a manual channel is never processed on this endpoint (it keeps its own URL and secret), and a request that mixes several workspaces is split: each workspace's delivery stores and processes only its own part, so one workspace's `webhook_events` never contain another workspace's messages.
- **Shared processing.** Both webhooks use `WhatsappWebhookProcessor` (dedupe by body hash, crash recovery of stale unfinished deliveries, ingest and status updates), so manual and platform channels behave identically. The manual path was refactored onto it with no behaviour change (existing tests untouched).
- **A phone number belongs to one workspace, enforced by the database.** Migration `20261118110000_whatsapp_phone_global_unique` adds a unique index on `channels(external_id)` for WhatsApp channels across all tenants (row-level security cannot hide a duplicate from a unique index; the migration refuses to run if duplicates already exist and reports only a count). Disabled channels keep their number reserved so re-enabling never collides. A second workspace connecting a taken number gets 409 `already_connected` before the one-time code is spent.
- **Connect flow** `POST /channels/whatsapp/embedded` (`integration:manage`, throttled, off unless `EMBEDDED_SIGNUP_MODE` is `mock` or `live`): the browser sends only `{code, phoneNumberId, wabaId, name}`. The server exchanges the code (a POST form body, so the secret and the code never appear in a URL), proves with the new token that the phone number is inside the WABA, subscribes the platform app to the WABA, seals the token and creates the channel. Nothing is stored unless every step succeeded. Reconnecting the same number in the same workspace refreshes it; a number connected manually must be disconnected first (409 `already_connected_manually`).
- **Disconnect** unsubscribes the app from the WABA, best effort and never blocking, and only when no other active Facebook-connected number of the workspace uses that WABA. Rotating credentials is refused for platform channels (connect again with Facebook).
- **Configuration.** `EMBEDDED_SIGNUP_MODE=off|mock|live` (default off). `live` requires `META_APP_ID`, `META_APP_SECRET`, `META_ES_CONFIG_ID`, `META_WEBHOOK_VERIFY_TOKEN` and `WHATSAPP_MODE=live`; `mock` needs `META_APP_SECRET` (it signs the test webhook) and is refused in production. The platform secret is never logged: the log redaction was widened to cover snake_case secret names and Meta `EAA…` tokens.

**Consequences.** The platform webhook is one shared point of failure for all Facebook-connected numbers (the existing `whatsapp_unprocessed` alert covers it). The platform secret is a high-value secret (secret manager, rotate on suspicion). The app owner (LeadPilot) becomes a Tech Provider: Meta business verification and app review are prerequisites, and the privacy policy, DPA and sub-processor list need rewording (see `docs/launch-checklist.md`).

## Milestone 2: the web side
- `GET /channels/embedded-signup` (integration:manage) tells the page `{mode, appId, configId, graphVersion}`. The app id and configuration id are public by design; the app secret is never included, and in `mock` mode no Facebook values are sent at all.
- `lib/embedded-signup.ts`: the Facebook SDK is loaded **only when the user clicks Connect** (never on page load). The pop-up answers twice, the SDK login callback with a one-time code and a window message with the phone number id and WABA id; a small collector needs both, in either order, and settles once. The message is accepted only from `https://www.facebook.com` or `https://web.facebook.com` (a look-alike origin or `http` is ignored), the ids must be digits, and a closed dialog is "cancelled", not an error. The browser forwards only `{code, phoneNumberId, wabaId}`; it never holds a token.
- `EmbeddedSignupButton` and the WhatsApp card: Facebook is the main button when the mode is not `off`; "Advanced: use my own Meta app" opens the manual form. Facebook-connected numbers show "nothing to set up in Meta" instead of a callback URL and verify token, and a disabled or errored one offers "Reconnect with Facebook". In `mock` mode (never in production) the button opens a small stand-in dialog that feeds the same server call, which is what the E2E test (`e2e/tests/18-embedded-signup.spec.ts`) drives.
- CSP (`next.config.ts`) now allows `connect.facebook.net` (script), `graph.facebook.com`, `www.facebook.com` and `web.facebook.com` (connect) and `www.facebook.com`, `web.facebook.com` (frames). This list follows Meta's documentation and is **not confirmed in a real run**: if the pop-up misbehaves, look for blocked requests in the browser console.
- Accessibility: axe reports no WCAG A/AA violations on the integrations page unconnected, with the stand-in dialog open, and connected, in light and dark; no horizontal overflow at 375 px. A toast caught mid-animation can trigger a false contrast report, so the test waits for toasts to leave (a settled toast was checked and is clean).

## Milestone 3: staying connected, Meta's callbacks, templates
- **A revoked token is a state, not a mystery.** New channel status `NEEDS_RECONNECT` (migration `20261118120000`): sends are already refused for any non-active channel ("channel_unavailable"), the card shows "Reconnect needed" with a Reconnect with Facebook button, and re-running Embedded Signup for the same number restores it. Two ways in, both flag the channel once and tell the owners once: (1) the **daily health check** (`ops/channel-health.ts`, run from the minute maintenance job, once per channel per day via an event mark) tests every Facebook-connected token with `getPhoneNumber`; only a definite "token invalid or expired" answer (Meta error codes 190, 102, 463, 467, non-retryable) flags it, a passing failure (Meta or the network) changes nothing and is retried on the next tick; a flagged channel whose token works again becomes active; a token Meta said will expire gets a warning 7 days ahead (only when Meta gave an expiry; unknown means no warning); (2) Meta's own **account notice** (`account_update` with a removal or uninstall event) on the platform webhook flags every Facebook-connected channel of that WABA at once, audits it, and queues an outbox event so the notifier creates the owner notification. A channel the owner disabled stays disabled. Only Facebook-connected channels are ever checked; manual channels are untouched.
- **Meta's required callbacks** (`channels/meta-callbacks.ts`, public, off while Embedded Signup is off): `POST /webhooks/meta/deauthorize` and `POST /webhooks/meta/data-deletion` take Facebook's `signed_request` (HMAC-SHA256 of the payload with the platform app secret, checked in constant time; algorithm and numeric user id validated). Data deletion answers `{url, confirmation_code}` and `GET /webhooks/meta/data-deletion/:code` plus the public page `/data-deletion?code=` show the status. **LeadPilot stores no Facebook profile data and no data keyed to a Facebook user**, so there is nothing to delete automatically: a request is recorded in `meta_data_requests` (platform-only table, invisible when a workspace is in scope; only a SHA-256 hash of the user id is kept, never the id) for the operator to follow up, and the status text says what is and is not held. Limit: the Facebook user id is not mapped to a channel (that needs Meta's token-debug call, not built), so a deauthorize cannot flag a channel by itself; the daily check and the account notice cover revocation.
- **Template sync** (read-only; `POST /whatsapp/templates/sync`, the "Sync from WhatsApp" button, and once after connecting): `GET /{waba}/message_templates` (paged, capped at 1000) into `whatsapp_templates` with `source`, `approval_status`, `synced_at` (migration `20261118123000`). Hand-typed templates are never overwritten (a clash is reported), synced ones are updated with Meta's status, synced ones Meta no longer lists are removed. **Only APPROVED synced templates can be sent**: a pending or rejected one is refused with `template_not_approved` and a plain message, in the inbox and in the automation preview; hand-typed templates behave exactly as before. Creating templates from LeadPilot is out of scope.
- New SECURITY DEFINER lookups return ids and status only: `list_platform_channels_for_health()`, `find_platform_channels_by_waba()`.

## Not verified (everything Meta-facing)
The live client calls follow Meta's documented Graph API at planning time and have never been run: `POST /oauth/access_token` (client id, secret, code), `GET /{waba}/phone_numbers`, `POST` and `DELETE /{waba}/subscribed_apps`. Unknown until a real run: the exact Embedded Signup configuration and the message the pop-up posts to the page, whether the code exchange needs a `redirect_uri`, the token's lifetime (the code stores an expiry only if Meta returns one), whether the phone must be registered with a PIN (not implemented), whether the WABA subscription must carry an override callback, the permissions that app review requires, and the exact Facebook hosts the web page must allow in its CSP (milestone 2). Milestone 3 handles revoked tokens (health check, `NEEDS_RECONNECT`) and Meta's deauthorize and data-deletion callbacks.
