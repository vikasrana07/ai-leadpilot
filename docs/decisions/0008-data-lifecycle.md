# ADR-0053 to 0058: data lifecycle (Phase 8, workstream F2)

Status: accepted (2026-11-17). Verified with tests and in a local browser; **not** verified against AWS/S3 in production, and the legal retention choices need a lawyer.

## ADR-0053 Retention is per workspace, bounded by the platform, and purged by one daily idempotent job
Settings live in `tenants.settings.retention`: raw webhook payloads (default 30 days), soft-deleted leads before hard purge (default 30 days), closed conversations and audit log (default **keep**). The platform sets defaults and a hard minimum (`RETENTION_*` env; minimum 7 days) so a workspace cannot configure its own data away by mistake; values below the minimum are rejected and also clamped at run time. The job runs from the minute scanner but is guarded by an `event_marks` row per workspace per day, so two workers or ticks cannot run it twice. Each run works in batches of 1000 (up to 20 batches), is a no-op when nothing is due, can be previewed (`POST /privacy/retention/preview`, counts only), and writes a counts-only audit entry. **Deletion happens in the `purge_retention` SECURITY DEFINER function**: the application role still has no `DELETE` on webhook payloads, messages or the append-only audit log. Records of privacy actions (`privacy.*` audit entries) are never aged out. Soft-deleted leads are purged through `erase_lead`, so everything linked to them (conversations, consents, raw payloads mentioning their phone) goes too.
Deleting a webhook-event row also drops its de-duplication hash; a provider redelivery after the retention window is accepted again but message ids stay unique, so no duplicate messages result.

## ADR-0054 Workspace export: asynchronous, owner-only, one at a time, no new dependency
`POST /privacy/exports` queues a `data_exports` row (a partial unique index allows one active export per workspace; the second request is 409). The worker builds one `workspace-export.json.gz` (Node's built-in gzip; no zip library is a direct dependency, so none was added): tenant profile and settings, members (name, email, role), and every table in `EXPORT_INCLUDED` (`apps/api/src/ops/export-tables.ts`) read page by page. **Every tenant table must be classified as included or excluded; a test fails when a new table is neither.** Excluded with reasons: hashed API keys, encrypted credentials, embeddings, internal queues and de-duplication markers, raw webhook payloads, platform-owned records. Redacted columns: invitation token hashes, channel webhook keys/config, knowledge-file storage paths. The file is stored under `tenants/<id>/exports/<id>/` in object storage, downloaded through the authenticated API (owner only, tenant-checked, audited), and deleted when it expires (7 days, `EXPORT_TTL_DAYS`). The owner is notified in-app when it is ready. Export routes stay available when the workspace is read-only (lapsed or pending deletion).
**Limit:** the document is assembled in worker memory then compressed; very large workspaces (millions of messages) need a streaming/chunked format. Tables are paged by physical row order, so rows changed during the export may be missed or repeated (not a point-in-time snapshot).

## ADR-0055 Workspace deletion: cooling-off, read-only, then a table-complete purge
The owner requests deletion with a reason, the exact phrase `DELETE WORKSPACE` and their **password** (re-authentication; rate limited). The workspace becomes read-only at once (`pending_deletion` 403 on writes; reads, export, billing and cancel stay open), a banner explains it, and owners are notified by in-app notice and email. The owner can cancel at any time for `DELETION_COOLING_OFF_DAYS` (default 14). Platform admins see pending requests in the console. After the period the worker, per workspace: cancels the provider subscription through the billing-provider interface (a failure is logged loudly and does not block the purge), deletes the object-storage prefix `tenants/<id>/`, then calls `purge_tenant`.
`purge_tenant` discovers every table with a `tenant_id` column at run time and deletes the workspace's rows (retrying around foreign-key order), so **a new table is covered by construction**; it raises if any table could not be emptied, then deletes the tenant row and every user account left with no workspace (accounts that also belong to another workspace survive). The function reports its retained tables and a test pins them to exactly `invoices`, `payments`, `platform_audit_logs`. Retained: invoices and payments (GST/Indian tax record-keeping; **the retention period and whether buyer details must be kept need confirmation from a chartered accountant/lawyer**) and a content-free platform audit record (`platform.tenant_purged`: counts only). Redis holds no per-workspace keys that outlive jobs, so nothing is purged there. The tenant row is deleted rather than kept as a `DELETED` tombstone (it is set to `DELETED` inside the function before deletion); sign-in for a purged owner fails because the account is gone.

## ADR-0056 Lead privacy actions in the UI
The lead page has a Privacy menu: *Export data* (JSON download from `/privacy/leads/:id/export`, needs `lead:export` + `lead:read:all`) and *Erase permanently* (needs `lead:delete`: owners; a dialog explains irreversibility and requires a reason and the typed word ERASE).

## Not built / open
Streaming export for very large workspaces; per-conversation retention rules by channel; legal review of retention defaults and of what must survive deletion; restoring a workspace after the purge (impossible by design; backups still contain the data until they age out; document the backup retention period to customers); notifying other processors (OpenAI/Meta) of deletion requests.
