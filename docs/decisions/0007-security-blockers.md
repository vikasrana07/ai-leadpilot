# ADR-0047 to 0050: security launch blockers (Phase 8)

Status: accepted (2026-11-17). **KMS and Cloudflare Turnstile were exercised only through test doubles/mocks, never against the real services.**

## ADR-0047 Master key: async providers, record-level key ids, KMS envelope
`MasterKeyProvider.wrap/unwrap` are now async. `SecretBox` keeps the existing envelope design (a fresh data key per record, AES-256-GCM, AAD = tenant + purpose) and only changes who wraps the data key: `LocalKeyProvider` (id `local-1`) or `AwsKmsKeyProvider` (id `kms:<KMS_KEY_ID>`, KMS `Encrypt`/`Decrypt` of the 32-byte data key with an encryption context). Selected by `KEY_PROVIDER`. Every record stores its `key_id`; `open` finds the provider from the record, so old local records stay readable after switching and a record under a rotated-away KMS key is read through KMS (which holds it). `SecretBox.rewrap` re-wraps only the data key (ciphertext and AAD untouched); `rewrap-secrets.js` migrates `integration_credentials` and `mfa_credentials` in place (owner role, compare-and-set on the old key id, idempotent, `--dry-run`). Production refuses `KEY_PROVIDER=local` unless `ALLOW_LOCAL_KEY_IN_PRODUCTION=true`.
**Dependency:** `@aws-sdk/client-kms` (same SDK family as the S3 client). **Tested with an in-memory fake KMS** (per-key material, encryption context bound, wrong key/context fails): rotation, key-id recording, tamper and wrong-key failure, local-to-KMS migration. **NOT run against AWS KMS**: IAM policy, regional behaviour, throttling and latency are unverified. Cost: one KMS call per secret read (credentials are read on every WhatsApp send/webhook): caching unwrapped data keys in memory for a short TTL is a likely follow-up if KMS latency or cost matters.

## ADR-0048 Bot protection: Cloudflare Turnstile, server-verified, fail closed
`BotGuard` on `POST /auth/register`, `/auth/login`, `/auth/forgot-password` and `POST /widget/sessions` reads `x-turnstile-token` and verifies it with Cloudflare over `fetch` (no dependency): missing token, rejected token, non-200, malformed body, network error and a 5 s timeout all DENY. The global rate limiter runs first and still applies. Modes: `off` (default; production refuses it unless `TURNSTILE_ALLOW_OFF_IN_PRODUCTION=true`), `mock` (only the literal token `mock-pass`; refused in production), `live`. The web forms render the Turnstile widget when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is set (`mock` skips the network); `widget.js` learns the mode from `/widget/config` and runs an interaction-only challenge before creating a session. Visitor messages after a session exists are not challenged (the session token is the proof). **Not verified against Cloudflare's real service or in a real browser with live Turnstile.** Lead-capture endpoints authenticate with API keys and are not challenged. Customers' sites need `challenges.cloudflare.com` in their own CSP.

## ADR-0049 MFA: TOTP on node:crypto, for users and platform admins
RFC 6238 (SHA-1, 6 digits, 30 s, ±1 step skew) implemented with `node:crypto`; checked against the RFC test vectors. Table `mfa_credentials` (global: MFA belongs to the person, `subject_type` = `user | platform_admin`) holds the secret envelope-encrypted (SecretBox, key id per row) and `last_used_step`: a code is accepted only for a step greater than the last accepted one, via compare-and-set, so a code can never be replayed, even by two simultaneous requests. 5 failures lock the credential for 10 minutes (counter resets on success); the verify endpoints are also IP-throttled. 10 random recovery codes are stored as SHA-256 hashes and consumed atomically (single use). Enrolment shows the key once (otpauth link and manual key, no QR image); recovery codes are shown once and the UI makes the user acknowledge them. Disabling or regenerating recovery codes needs a current code or a recovery code.
**Login:** a correct password for an enrolled account returns `{mfaRequired, challengeToken}` and no session or cookie; the challenge is a 5-minute JWT with its own audience (`mfa-challenge:user` signed with the access secret, `mfa-challenge:platform_admin` with the platform secret), so a tenant challenge cannot complete a platform login or the reverse. `POST /auth/mfa/verify` (tenant) and `POST /platform/auth/mfa` complete it. Audit events: `auth.mfa_enrollment_started|enabled|failed|recovery_code_used|disabled|recovery_codes_regenerated` (user audit log, or the platform audit log for admins).
**Workspace policy:** owners (`settings:manage`) can require MFA (`PUT /security/workspace`; they must be enrolled first). `TenantGuard` then answers `403 mfa_enrollment_required` for tenant routes to members without MFA; `/auth/*` and `/security/mfa/*` are not tenant routes, so they can still enrol. A member cannot disable MFA while the workspace requires it. `PLATFORM_REQUIRE_MFA=true` does the same for platform admins (only `/platform/security/*` is reachable until enrolled).
**Not built:** WebAuthn/passkeys, SMS/email codes, remembered devices, admin-initiated MFA reset UI (a schema-owner SQL delete after identity verification is the documented fallback), enforcing MFA on API-key or refresh flows (a session that exists stays valid; MFA is checked at sign-in).

## ADR-0050 Scope and honesty
These close the three launch blockers named in `docs/security-review.md`. They do not replace an independent security review, and none of the third-party integrations (AWS KMS, Cloudflare Turnstile) has been run for real.
