# ADR-0059 to 0064: public API, outbound webhooks, reports and support access (Phase 8, F3)

Status: accepted (2026-11-17)

## ADR-0059 One key system, two surfaces
API keys (`api_keys`, `lp_live_…`, SHA-256 hash only, shown once) already existed for server-to-server lead capture. They were **extended, not duplicated**: keys now carry scopes (`leads:create|read|write|delete`, `conversations:read`, `appointments:read|write`), an optional expiry, `last_used_at` and a request counter. The original `POST /public/leads` keeps working with the `leads:create` scope on every plan. The versioned public API lives under `/v1` and authenticates only with a key (`Authorization: Bearer lp_live_…`); session JWTs are not accepted there and keys are not accepted anywhere else (both tested).
`@Public()` on `/v1` only switches off the session guards; `ApiKeyGuard` protects every route (the route-inventory test asserts all `/v1` routes answer 401 anonymously, except the OpenAPI description).

## ADR-0060 A key can never exceed its scopes, and acts as a machine actor
`ApiKeyGuard` resolves the tenant from the key (a `SECURITY DEFINER` lookup by hash, extended to return expiry), then checks: unrevoked, unexpired, **plan includes `api_access`** (402 `feature_not_in_plan`), workspace not read-only for writes (402 `subscription_required`), per-key rate limit (default 120/min, Redis-backed across instances, 429 + `Retry-After`), route scope (403 `insufficient_scope`). Scopes map to a fixed set of internal permissions (`SCOPE_PERMISSIONS`); no scope ever grants team, billing, integration, settings or privacy permissions. Existing services are reused unchanged (they already take an `Actor`), so row-level security, validation, audit and domain events behave exactly as in the app; audit entries carry the `apiKeyId`. Notes are attributed to the key's creator (the note table requires an author).
**Idempotency:** `Idempotency-Key` on POSTs (8-128 chars): first request runs, a retry with the same key and body replays the stored response (`Idempotent-Replay: true`), the same key with a different body is 422, a retry while the first is running is 409, a failed request releases its key. Stored per tenant in `idempotency_keys` (RLS).
**OpenAPI** (`/v1/openapi.json`, public, no data) is generated from one list of routes plus the real zod schemas (`z.toJSONSchema`) for request bodies; a test fails if the document and the controller's real routes differ.
**Deliberately not in v1:** permanent erasure (a privacy workflow with confirmation, owner-only), team/billing/integration management, sending messages (needs a consent/24-hour-window design of its own).

## ADR-0061 Outbound webhooks ride the outbox, and their transport is SSRF-hardened
The relay already processes each committed domain event once in a tenant transaction; it now also inserts one `webhook_deliveries` row per subscribed, enabled endpoint (unique per endpoint and event, so replays cannot duplicate). Sending is a separate step: `claim_webhook_deliveries` (`SKIP LOCKED`, 2-minute lease, any number of workers) → signed POST → outcome recorded. **Deviation from the brief:** deliveries are DB-driven (state + `next_attempt_at`), not a BullMQ queue: it is crash-safe by construction, works without Redis and is trivially testable; BullMQ adds nothing here.
- **Signing:** `X-LeadPilot-Signature: v1=HMAC-SHA256(secret, "<timestamp>.<raw body>")` plus `X-LeadPilot-Timestamp` (receivers should reject anything older than 5 minutes), `X-LeadPilot-Event`, `X-LeadPilot-Delivery`. Per-endpoint secret `whsec_…` shown once, stored envelope-encrypted (`SecretBox`, AAD = tenant + endpoint), rotatable (the old one stops working at once).
- **Payloads carry ids only** (`{id, type, createdAt, test, data:{leadId…}}`): no names, phone numbers or message text leave the platform in webhooks; receivers fetch details through the public API under their own key's scopes.
- **SSRF:** HTTPS only; userinfo, odd ports-on-literals and obfuscated hosts are refused; the host is **resolved once at send time**, every address must be public (blocks 0/8, 10/8, 100.64/10, 127/8, 169.254/16 incl. cloud metadata, 172.16/12, 192.168/16, multicast, reserved, and IPv6 loopback, link-local, ULA, IPv4-mapped/compatible, NAT64 and 6to4 forms embedding those), and the connection is made **to that exact address** (TLS SNI/Host keep the name), so DNS rebinding cannot swap the target between check and connect. Redirects are never followed (a 3xx is a failure), 8 s timeout, response snippet capped. The same checks run when an endpoint is saved. `WEBHOOK_ALLOW_PRIVATE_TARGETS` exists for local tests only and is **rejected in production**.
- **Reliability:** backoff `base × 4^(n-1)` (default 30 s base, 6 attempts, cap 6 h), then `FAILED` (kept, with reason, and manually redeliverable); a blocked-target failure is terminal at once. 10 consecutive exhausted deliveries switch the endpoint off and notify the owners. "Send test event" delivers immediately and shows the outcome. The delivery log stores status, latency, error and the payload that was sent, nothing else.
- Plan gating: `api_access` (new entitlement, Growth/Premium/internal on, Starter off, editable in the platform console); events stop being queued when the plan loses it.

## ADR-0062 Reports are live queries with hand-checked fixtures
Seven reports (acquisition, funnel, agents, response time/SLA, appointments, AI, automations), each returning summary figures, chart series and tables, computed per request from tenant-scoped SQL (no rollups, no sample data). Scope: managers/owners see the workspace; an agent sees only reports about their own leads and conversations (people-comparison, AI and automation reports are manager-only, 403 otherwise). Filters: today, yesterday, 7d, 30d, this month, custom (≤ 13 months), in the workspace timezone. CSV export per table: plan-gated (`csv_export`), audited, formula-injection neutralised, BOM-prefixed for Excel. Correctness is pinned by a fixture whose expected values were worked out by hand (`reports.test.ts`). Definitions that matter: *funnel* = of leads created in the period, how many have ever been in each stage (current stage ∪ stages moved into); *response time* = first inbound message to the first outbound AI/agent message, per conversation created in the period, against the workspace SLA target; *show rate* = completed ÷ (completed + no-show).
**Performance at 100k leads** (local, one tenant with 100,000 leads / 10,000 conversations / 60,000 messages / 10,000 appointments): all reports 25-210 ms for the month/30-day ranges. The first funnel query took 1.28 s (a correlated lookup per lead and stage); rewritten set-based it takes 35-70 ms. No new index was needed.

## ADR-0063 Support access: read-only, bounded, confirmed, visible, switchable off
A platform admin can open a **support session** in a workspace. It is the riskiest feature of the console, so every control is enforced server-side in one place (`AuthGuard` hook + `support-access.ts`), not in the UI:
- **Start:** console login + a written reason (≥ 10 chars) + **password re-entry** (same lockout as login) + workspace active + owner has not switched support access off; at most **30 minutes**. A `support_access_sessions` row is created (platform-only RLS: invisible inside any tenant context).
- **Token:** a JWT with its **own audience** (`tenant-support`), set as the workspace access cookie; a normal login token is never a support token and vice versa. Validity is re-checked on every request through `support_session_active()` (unexpired, not ended, workspace active, owner setting), so ending, expiry, suspension or the owner's switch take effect on the next call.
- **Read-only:** every non-GET is refused with 403 `support_session_read_only` before any handler runs, on every route including those that skip tenant checks; the single exception is ending the session. **Blocked entirely** (403 `blocked_for_support`): team, roles, billing (except the plan summary the banner needs), integrations/channels, API keys, webhooks, privacy, audit logs, knowledge files, notifications, live stream, auth/MFA/sessions, anything named export/download/media. The synthetic member holds only read permissions (leads, conversations, appointments, analytics, properties, usage).
- **Visibility and audit:** an un-dismissible banner (who, why, minutes left, End button); the workspace owners get an in-app notification and an email at start and end; every allowed request and every blocked attempt is written to **both** the platform audit log and the tenant's own audit log (method + path, no bodies; refused live-stream reconnects are not audited to avoid noise).
- **Owner control:** Settings → Support access switches it off entirely (open sessions end at once; new ones are refused and the refusal is logged).
**Known limits:** a support session *can read personal data* (that is its purpose; the reason, the customer notice and the audit trail are the control, and the policy documents should say so). It replaces the workspace login cookie in that browser, so support staff should use a separate browser profile. MFA for platform admins is F1's lane and applies to the console login that precedes this.

## ADR-0064 Scope and what is not verified
Built and tested: everything above. **Not verified:** the public API and webhooks under real network conditions (TLS receivers, public DNS, IPv6, slow or hostile receivers beyond the local tests); delivery behaviour with several worker processes under load; the web pages on mobile and with keyboard-only navigation; multi-instance rate-limit accuracy in Redis (single-process verified); API clients/SDKs (none exist). Webhook delivery ordering is not guaranteed (events are independent; use `createdAt`/ids).
